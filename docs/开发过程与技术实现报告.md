## 第一部分:系统总体架构

项目是单体仓库(monorepo),由六个运行单元组成:

| 单元 | 技术栈 | 职责 |
|---|---|---|
| `apps/web` | Next.js 16 / React 19 / CSS Modules / Vitest | 学习者工作区界面;同源反向代理(`​/api/[...path]`)把浏览器请求转发给 API,解决端口与 Cookie 域问题 |
| `apps/api` | FastAPI / SQLAlchemy 2 / Python 3.12 | 全部业务 HTTP 接口、鉴权、知识库管线调度、支付 |
| `apps/agent-runtime` | Node.js 24 / TypeScript(宿主机进程) | AI 助教 Agent 运行时:会话、回合、事件流、工具与技能执行 |
| `packages/agent-protocol` | TypeScript | API 与 Runtime 之间的事件/能力协议契约(共享类型) |
| worker 容器 | 与 API 同镜像 | 数据库租约队列消费者:解析、索引、候选生成、对象删除 |
| 基础设施 | PostgreSQL 17 + pgvector、Redis 7.4、MinIO | 关系数据+向量、缓存拓扑、对象存储 |

数据库迁移使用 Alembic,当前链 `0001_identity` → `0022_object_deletion_outbox` 共 22 个迁移。CI(`quality.yml`)运行 Ruff、pytest(覆盖率门槛 90%)、前端 Vitest/Lint/Build。

安全基线:所有密码用 argon2 哈希;会话为 HttpOnly Cookie + 服务端令牌摘要(数据库不存明文令牌);对象存储给应用下发最小权限独立身份;引用令牌用 HMAC 签名做成不透明串;`.env` 全部真实密钥不入库;Agent Runtime 只绑回环地址,容器经 `host.docker.internal` 访问。

## 第二部分:各功能如何实现

### 2.1 账号、空间与班级

- 注册/登录/登出(`identity/router.py`):argon2 校验密码;登录成功颁发随机会话令牌,数据库只存其 SHA-256 摘要,浏览器持有 HttpOnly Cookie;登录与注册分别做 IP 限流(默认 5 次/15 分钟),防止爆破与批量注册。
- 空间:每个用户自动获得"个人空间";班级空间由班级功能创建。所有知识库、会话、钱包都挂 `space_id` 做租户隔离。
- 班级:任意用户可建班级(同时建班级空间,创建者为 Owner),支持受限邀请码(次数/有效期/角色),Owner 可调整成员角色或移除。

### 2.2 知识库:从原始资料到可检索知识

完整管线由三个异步任务组成,全部走数据库租约队列:

1. **上传**(`POST .../documents`):前端生成幂等键,后端校验扩展名(PDF/DOCX/UTF-8 Markdown/JPG/PNG/Obsidian Vault ZIP)与大小上限(100 MiB),文件写入 MinIO,落库文档与版本,并投递 `parse_document` 任务。幂等键保证同一请求重试不会产生重复文档。
2. **解析**(`parse_document`):PDF 用 pypdfium2 逐页渲染出文本与页面图,DOCX/Markdown 直接抽取,图片走 OCR 通道;解析结果被分类为标题/段落/公式/表格/图注/例题/答案等语义块,持久化为不可变文档版本(Block 级),并生成页面预览对象。
3. **建索引**(`build_index`):对语义块分块,做词法词项归一化(含中文),用确定性哈希嵌入(384 维)写入 pgvector;每次构建生成带签名的索引版本,完成后原子切换 ACTIVE,旧版本退役。

**检索**是混合检索:词法(词项交集打分)+ 向量(余弦相似度,阈值 0.2)两路召回,用倒数排名融合(RRF,k=60)排序;返回有界摘录(500 字符,词法命中点对齐),引用令牌是 HMAC 混淆的块 ID,可"打开原页"验证原文(带 Range 的对象流)。

**AI 导师检索模式**:为助教提供 `full_content=True` 开关——命中块直接返回完整原文而非摘录,配合 12 块上限与 2 万字符总量预算,保证模型读到的是知识库原文而非切片。

### 2.3 知识候选:人工审阅确认闭环

对已索引文档可发起 `generate_markdown` 任务,分三段并发执行(线程池,并发度可配):

1. **结构候选**:按上下文块(每块 60k 字符)让模型输出章节结构提案;
2. **公式证据**:对含公式块从维基百科官方 API 抓取佐证(白名单域名);
3. **知识候选**:结合结构提案与公式证据,按严格 JSON 契约生成概念/性质/公式/方法/示例候选,以及候选间的层级链接。

三段输出都经过"失败即拒绝"的 JSON 解析与字段级校验(别名归并、悬空引用降级、禁止伪造 wikilink)。候选进入 `needs_review` 批次,学习者在网页上**逐项勾选接受/拒绝**后确认,才转正为正式知识笔记并写入层级链接。历史版本全部保留(`MarkdownRevision`)。

### 2.4 AI 助教(Agent 平台)

这是上游交付的核心演进,当前实现为两代并存:

- **旧版 tutor 接口(保留只读)**:Faro 聊天补全,提示词强制"仅依据摘录回答,证据不足要明说",回答携带 `[1]` 式引用,可点击打开原页。
- **新版 Agent 架构(主力)**:
  - **宿主机运行时**(`apps/agent-runtime`,Node 24):因为 Agent 需要执行工具/技能、跑子代理,放在容器外以宿主进程运行,只绑定 `127.0.0.1:8765`;API 容器经 `host.docker.internal` 访问,鉴权用 `AGENT_RUNTIME_TOKEN`,事件完整性用 `AGENT_CAPABILITY_SECRET`。
  - **会话模型**:`agent/sessions` → `turns` → 持久化事件流;事件先落库再重放,支持 WebSocket 流式推送、fork/resume/rewind/stop。
  - **双证据接地**:提示词把"知识库摘录"与"网页摘录"都标记为不可信数据,要求优先依据知识库证据,回答必须沿用 `[K1]`、`[W1]` 引用标记,不得伪造来源。
  - **能力与安全**:能力开关(哪些工具可用)、MCP 配置路径、技能路径、子代理/工具并发上限;诊断端点暴露运行时与供应商健康。
  - **前端**:`agent-panel.tsx` 组合输入区、设置页、工具卡片与事件时间线;所有事件经 API 代理,浏览器不直连 Runtime。

### 2.5 题库与复习闭环

- 出题必须锚定具体知识块(存 `source_content_sha256` 与指针),保证题目可溯源。
- 作答提交带幂等键 + PostgreSQL advisory lock,防止双击重复计分。
- 判分是确定性规则:选择题按选项,简答/开放题按关键词覆盖率(含中文归一化),错因三分类(无/元认知/应用)。
- 掌握度按最近 5 条证据做时间衰减加权;复习调度按知识类型(记忆/概念/程序/设计)走固定间隔序列;提交后揭示正确答案与解析(`expected_answer`/`explanation`)。

### 2.6 积分与支付(1 积分 = 1 元)

- **账本**:`Wallet`(CNY,Decimal(20,8))+ 追加式 `LedgerEntry`(充值/消费/冲正三类),余额=账本求和;预扣(reservation)机制支持先冻结后结算。任何人工充值必须有唯一外部流水号与操作人,冲正生成配对负项,历史不可改写。
- **自助充值订单**:`RechargeOrder` 记录订单号(唯一)、金额、渠道、状态与网关原始回调;**入账唯一路径**是网关回调确认函数——按订单号行锁、校验金额一致、写充值账本与审计记录;金额不符标记 `paid_mismatch` 绝不自动入账;重复回调天然幂等。
- **支付宝(RSA2 电脑网站支付)**:按规范对顶层参数排序拼接后私钥签名生成收银台 URL;回调验签时剔除 `sign/sign_type` 再验 RSA2,并核对 `app_id`。
- **微信支付(APIv3 Native 扫码)**:请求用商户私钥做 SHA256withRSA 签名(`WECHATPAY2-SHA256-RSA2048`);平台证书从 `/v3/certificates` 下载(报文本身是 APIv3 密钥 AES-256-GCM 加密),按序列号缓存并随轮换刷新;回调验签 + 解密 `resource` 后核对商户号/AppID/金额;金额以"分"交互、"元(积分)"入账。
- **本地模拟渠道**:mock 收银台走与真实回调完全相同的入账代码路径,便于开发与 CI。
- **前端账户面板**:余额、流水(充值/消费/冲正)、金额预设与自定义金额、渠道展示(按部署激活项),支付宝跳转收银台、微信渲染扫码二维码并轮询到账。

### 2.7 Worker 租约队列与运维参数

- 任务表 `ingestion_jobs`:状态机 `queued → running →(retry_wait)→ completed/failed/cancelled`;领取即写 `lease_owner/lease_expires_at`,超时未完成可被重新认领;失败按 1 分钟退避重试,最多 6 次。
- 关键可调参数(均经 compose 从 `.env` 注入):`FARO_MAX_CONCURRENCY`(候选生成三段的 LLM 并发)、`WORKER_LEASE_MINUTES`(租约时长)、OCR 开关、上传与 Vault 限额。
- 多 worker 水平扩容天然安全:租约互斥保证同一任务只被一个实例处理。

## 第三部分:开发中遇到的真实问题与解决过程

以下全部是本项目开发中实际发生、实际解决的问题,按主题归类。

### 3.1 环境与依赖类

1. **本机 Python 版本不匹配导致测试无法收集**。项目锁定 Python 3.12,而开发机仅有 3.13/3.11,anaconda 环境还装了过旧版本的 argon2(`InvalidHashError` 导入失败)。解决:不在本机硬凑环境,统一用项目镜像 `textbook-tutor-api:local` 挂载仓库跑测试,与 CI 行为一致。
2. **旧镜像缺新依赖**。worker 启动报 `ModuleNotFoundError: httpx`。原因:镜像是在依赖更新前构建的。解决:按 README 用 `--build --no-cache` 重建 api/worker,禁止在容器内临时 pip install 掩盖问题。
3. **占位密钥被当成"已配置"**。`.env` 示例里的 `replace-with-your-faro-api-key` 是非空字符串,服务误报"模型已配置",实际调用全部 401,表象是"莫名的网络故障"。解决:增加占位符识别(placeholder/replace-with/changeme 等),不认识的一律视为未配置,前端如实显示"模型待配置"。

### 3.2 网络与镜像源类(本项目最凶险的一类)

4. **清华 PyPI 镜像对本机返回 403**。症状是所有包 `from versions: none`(pip 全局 index-url 配了清华源)。用 `curl` 分别探测官方源与清华源定位到是镜像侧拒绝。解决:所有 pip 操作显式 `-i https://pypi.org/simple`。
5. **Docker 构建失败(同一根因的第二层)**。Dockerfile 把 `PIP_INDEX_URL` 写死为清华镜像,`docker compose build` 在 pip 安装步失败。解决:把 `PIP_INDEX_URL`、`DEBIAN_APT_MIRROR`、npm registry 全部改成**可覆盖的构建参数(ARG)**,compose 从 `.env` 透传,默认值为官方源。
6. **官方 Debian 源的 CDN 超时**。改成官方源后 apt 又失败:`deb.debian.org` 的包下载走 Fastly CDN,直连超时(此前能构建成功纯靠层缓存)。实测阿里/中科大/华为/163 镜像均可用,选择阿里镜像写入本机 `.env` 的 `DEBIAN_APT_MIRROR`。经验教训:**构建源必须是"环境参数"而不是"仓库常量"**。
7. **pnpm 访问 npmjs 官方源超时**(与 Fastly 同族问题)。解决:`pnpm install --registry=https://registry.npmmirror.com`。
8. **供应商直连抖动**。Faro API 在部分网络下时通时断,曾出现整批任务连环失败。解决:网络客户端带指数退避重试(仅网络/超时/429/5xx 重试,401/请求形状错误不重试),另备受限 CONNECT 中继作为可选逃生通道。

### 3.3 业务正确性类

9. **中文检索召回失效**。中文分词后的词项与查询归一化不一致导致命中失败。解决:统一词法归一化管道并补回归测试(中文查询命中中文文档)。
10. **真实大模型输出形状不可控**。候选生成要求严格 JSON,真实模型输出存在字段别名/缺失/悬空引用。解决:实现"宽松解析+失败即拒"——字段别名归并、可降级项降级、致命项报稳定错误码,并配单测覆盖各种畸形输出。
11. **占位 OCR 后端**。仓库安全默认 `OCR_BACKEND=disabled`,扫描版 PDF 解析必然报 `ocr_disabled`。这是有意的边界(不把不可用的能力伪装成可用);对扫描件的正确姿势是使用文字版资料,或后续显式启用 tesseract 后端(镜像内已安装)。
12. **候选生成对大文档"永远失败"**(最重要的一个)。症状:《AI-Agents-in-Depth》PDF 生成知识候选连续 6 次失败。数据库实测:解析 7 分钟、建索引 10 分钟、候选生成超过 5 分钟——而 worker **任务租约写死 5 分钟**,跑到一半租约过期,被判 `worker_lease_exhausted`,重试必然在同一位置死亡。解决:新增 `WORKER_LEASE_MINUTES` 配置(默认 5,范围 1-240)并写入 compose 与文档;同时把 `FARO_MAX_CONCURRENCY` 从 2 提到 6 加速三段流水线。验证:调整后队列恢复流动,积压清空。
13. **毒任务阻塞队列**。上述必败任务持续重试,占住唯一 worker,让排队任务全部等待。解决:提高并发与租约后让其自然跑完;同时明确运维手段(失败任务到达上限自动停,或人工取消)。
14. **单测伪造的密钥缺参**。并发信号量、系统提示词透传等接口演进后,测试中的假适配器签名不同步导致失败。解决:测试与产品代码同评审同修改,保持"假适配器也是契约"。

### 3.4 合并与接口契约类

15. **迁移编号撞车**。合并上游时,双方各自新增了 0016/0017/0018(上游:agent 工作台/事件时间戳/对象删除出箱;本地:消息形态/充值订单/题库生成),形成两个 Alembic 分支头,`upgrade head` 会报多头错误。解决:把上游三条迁移整体顺延为 0020/0021/0022,修正 `revision/down_revision` 与文件内注释,同步更新测试中的 head 断言,恢复单链。
16. **合并后函数缺失**。上游重写的 `knowledge/service.py` 覆盖掉了本地新增的 `list_knowledge_documents`、`list_document_chunks` 与 `KnowledgeDocumentSummary/KnowledgeDocumentChunk` 数据类,路由导入直接失败。解决:以函数清单对比(HEAD vs 合并结果)逐个搬回,并核对路由依赖清单。
17. **响应契约字段冲突**。本地给导师消息加的必填 `kind` 字段与上游响应构造冲突(上游不构造该字段)。按"AI 助教以上游为准"的策略,从响应模型中移除该字段(数据库列保留默认值,不破坏数据)。
18. **重复定义**。搬运过程中与上游自带的同名数据类重复。解决:ruff F811 检出后删除冗余定义。

### 3.5 前端测试与渲染类

19. **jsdom 原生表单校验拦截提交**。金额输入框带 `min/max`,测试点击提交按钮时浏览器约束直接拦截,自定义校验永远不执行。解决:表单加 `noValidate`,统一走自定义校验与提示。
20. **React effect 中同步 setState 触发 lint 错误**。重构为"订阅回调中更新"模式(在 `.then` 回调里 setState),与仓库既有组件保持一致。
21. **CSS Module 类名契约**。组件引用了尚未定义的样式类(合并/新增功能时漏写)。仓库有专门的回归测试扫描"组件引用的每个类必须在 CSS 模块中定义",按报错补齐缺失类。
22. **模型输出直接显示 Markdown 源码**。AI 回答里的 `##`/`**` 以纯文本露出。解决:实现零依赖的富文本渲染器(标题分级/加粗/列表/行内代码),全部输出 React 元素、不经过 HTML 注入,模型输出中的任何 HTML 会被转义;并配"未闭合符号按字面保留""HTML 不执行"等测试。
23. **AES-GCM 参数顺序**。微信回调解密测试中把 `encrypt(nonce, data, aad)` 参数顺序写反,报类型错误。对照库签名修正。

### 3.6 Agent 运行时类

24. **面板报 `503 runtime_unavailable`**。运行时是合并后新增的宿主机进程,未安装未启动。解决:运行官方安装脚本(构建运行时并注册登录自启),再用官方启动脚本拉起。
25. **启动后报 `faro_not_configured`**。启动脚本在部分调用环境下未能把 `.env` 中的 `FARO_API_KEY` 注入子进程。解决:以"读取 `.env` 全量 → 构造进程环境 → 启动 node"的方式拉起,运行时诊断端点确认 provider 状态 `ok`,端到端发消息获得模型真实回复。
26. **PowerShell 5.1 兼容**。安装脚本在相对路径调用下 `$PSScriptRoot` 为空、`&&` 分隔符不受支持。解决:调用时显式传绝对路径 `-RepositoryRoot`,并避免 `&&` 语法。

## 第四部分:如何上传 GitHub,以及过程中遇到的问题

### 4.1 远端拓扑与凭据

- 仓库有两个远端:`origin`(团队组织仓库,主仓)与 `fork`(个人镜像)。历史上个人账号曾被平台标记(OAuth 与推送全挂),恢复后仅保证拉取可用,因此**正式提交一律走 origin 直推**(使用本机凭据管理器中的授权)。
- 推送前先 `git ls-remote` 核实连通性与分支占用,不盲目推。

### 4.2 上传流程(实际执行步骤)

1. **敏感信息隔离**:`.env`(全部真实密钥)、诊断日志均被 `.gitignore` 覆盖;提交前用 `git check-ignore` 复核,确保密钥永不入库。
2. **建功能分支**:从当前 HEAD 创建 `feature/aiopc-upgrades`,把 72 个变更文件以单条里程碑提交收口(提交信息按仓库惯例:类型 + 中文摘要 + 分模块正文)。
3. **推送功能分支**:`git push -u origin feature/aiopc-upgrades`,成功后用 `ls-remote` 核对远端指针与本地一致。
4. **更新 main**:由于功能分支包含旧 main 的全部历史,把 main 快进到功能分支是自然选择。

### 4.3 上传过程中遇到的问题与解决

1. **推送被拒(non-fast-forward)**:第一次把功能分支推到 main 时被拒——几分钟前队友刚给 main 推了一个新提交(文档审计记录)。**绝不用强制覆盖**:先 `git fetch` 看对方改动(仅三个文档文件、+20 行),把它合并进功能分支(自动合并无冲突),再推送,最终 main 是一次快进更新——既包含完整新项目,也保留队友的提交与全部历史。
2. **fetch 拿不到非 main 分支**:`git fetch origin` 长期不更新其他远端分支。根因是仓库对 origin 的 fetch refspec 只配置了 main。解决:检查其他分支一律用 `git ls-remote`(以远端为准)或显式 `git fetch origin <分支名>`。
3. **把"引用不存在"误判为"有新提交"**:用 `merge-base --is-ancestor` 批量判断时,已删除的远端引用会以非零退出并被误读。修正:判断前先 `ls-remote` 确认引用存在。
4. **误删被复用的组件**:按"孤儿清理"删除富文本渲染器后,发现它已被三个面板复用,立即从 HEAD 恢复。教训:删除前先全仓搜索引用。
5. **大体积锁文件冲突**:上游重写了 `pnpm-lock.yaml`(新增 agent 协议包),本地新增了 qrcode 依赖。解决:锁文件取上游版本,再以 npmmirror 源执行 `pnpm install` 重新调和,自动把 qrcode 写回锁文件。
6. **CRLF/LF 行尾干扰脚本化编辑**:Windows 检出把部分文件转成 CRLF,基于精确字符串匹配的脚本替换失败。统一按"读入后归一化为 LF、写回 LF"处理。
7. **上传后的三重验证**:①`git ls-remote origin main` 核对远端指针;②本地 `git log origin/main` 对照;③用 GitHub 网页/API(独立于 git 协议)确认最新提交哈希、作者与时间。三者一致才宣告上传成功。
