# LLM Markdown 知识库导入与双向链接设计

## 目标

将 Word、PDF、图片和 Obsidian Vault 导入为可编辑的 Markdown 知识内容，并在导入过程中接入 Faro 的 Gemini 模型进行全文整理；同时提供可靠的双向链接、反向链接和未解析链接索引。

## 已确认边界

- 采用 LLM 全文重写模式，而不是只做标题或摘要增强。
- 原始 Word/PDF/图片永远保留，LLM 生成的 Markdown 是独立草稿版本。
- 草稿必须经过用户预览、编辑和确认后才能成为正式知识内容。
- 不以章节总字数作为成功条件；只按模型上下文窗口分块。
- 只将空响应、明显截断、模型错误文本混入等情况标记为异常。
- 双向链接必须由 Markdown 中的显式 `[[笔记名]]` 语法确定性解析；LLM 建议的链接不能自动写入正式内容。
- Faro API Key 只允许存在于后端运行时环境变量中，不进入前端、数据库、日志或 Git。

## 方案

### 1. 导入流水线

```text
原始文件
  -> 原生解析 / OCR
  -> 带页码和来源指针的结构化块
  -> 按模型上下文窗口分块
  -> Faro Gemini Markdown 重写
  -> Markdown 草稿校验
  -> 用户预览与编辑
  -> 确认发布
  -> 双向链接索引与全文检索索引
```

原生解析器继续负责文件格式、安全边界、页码和原始来源；LLM 只接收结构化内容，并明确要求不要执行或采纳文档中的指令性文字。每个生成块保留来源页码或 source pointer，以便草稿和正式笔记都能回看原文。

长文以 token/context budget 为边界分块。章节可以很短或很长，不能用固定字符数、固定页数或输出长度判断章节是否有效。跨块时保留标题层级和必要的前后文，最终由合并器生成完整 Markdown。

### 2. Markdown 草稿与正式版本

导入结果增加独立的 Markdown 草稿状态，至少包括：处理中、草稿可预览、需要检查、已发布、失败。原始文档和生成 Markdown 具有独立版本与哈希，重新生成不会覆盖原始资料，也不会静默替换已发布版本。

草稿预览页面支持：

- Markdown 源码与渲染结果切换；
- 编辑后保存草稿；
- 查看异常提示和来源页码；
- 确认发布；
- 失败任务重试。

LLM 失败时保留原文、解析块和失败原因的稳定公开错误码；不把供应商原始错误、Key、请求体或堆栈返回给浏览器。

### 3. 双向链接索引

发布后的 Markdown 由确定性解析器处理：

- 解析 `[[笔记名]]`、`[[笔记名#标题]]` 和可选别名；
- 规范化笔记名和标题，保留原始显示文本；
- 建立 source note -> target note 的正向边；
- 反向查询生成 backlinks；
- 目标不存在时记录 unresolved link，目标笔记后来创建或改名时重新解析；
- 只把显式链接写入知识图谱，不把 LLM 的猜测自动当成事实。

全文搜索与显式链接索引是 Obsidian 基础体验的核心，不依赖 embedding。语义检索和自动关联保留为后续可选能力。

正式知识库默认采用稀疏层级图，而不是全连接关系图：

- 层级按“教材/文档 -> 章 -> 节 -> 小节或知识点”逐级递进；
- 正式 `[[Wikilink]]` 和 `markdown_links` 只记录直属父子关系，父节点列直属子节点，子节点回链直属父节点；
- 重复术语、公式复用、方法比较和一般引用保留在“语义关系（不参与关系图）”纯文本区，不写入图边；
- 接受子节点时必须同时接受其直属父节点，防止正式知识库产生孤立节点；
- 原始资料、候选关系和版本记录继续保留，因此压缩关系图不会丢失审核证据。

### 4. Faro LLM 适配

新增服务端 LLM provider adapter，使用教程中确认的 OpenAI 兼容协议：

- Base URL：`https://faroapi.com/v1`；
- API Key：运行时环境变量注入；
- Model：使用 Faro 模型广场当前显示的完整模型 ID，例如 `gemini-3.7-flash-tiered`；
- 只允许服务端调用；
- 设置单次请求超时、有限重试、上下文预算和并发上限；
- 记录脱敏的 provider、model、request id、token usage 和稳定错误码；
- 不在当前阶段假设 Faro 提供 embedding 接口。

如果未配置 Key 或模型，知识库的原生解析和草稿降级能力仍可工作；只有 LLM 重写步骤显示为不可用，不能把整条知识库导入链路伪装成成功。

## 验收标准

- DOCX/PDF 导入后保留原始文件，并能生成独立 Markdown 草稿。
- 短章节、长章节和多页章节均不会因总长度被拒绝。
- LLM 返回空内容、截断内容或错误文本时，任务进入可重试的检查/失败状态，原始文件不受影响。
- 用户确认前，草稿不会进入正式知识库检索结果。
- 发布后的 `[[链接]]` 能显示目标笔记和反向链接。
- 未解析链接可见，目标笔记创建后可重新解析。
- 没有 Faro Key 时不会泄露配置细节或产生虚假“AI 处理成功”状态。
- API、worker、Markdown 解析、链接索引、前端预览和失败重试均有自动化测试。

## 风险与取舍

- LLM 全文重写存在遗漏、误改和格式漂移风险，因此原始资料不可覆盖、草稿必须人工确认。
- Faro API 是外部付费依赖，必须提供预算、超时和重试边界；不在前端暴露 Key。
- 没有 embedding 时，自动语义关联能力有限，但不影响 Obsidian 风格的显式链接、反向链接和全文搜索。
- OCR、PDF 版面还原和公式转换可能需要独立增强，不把这些问题伪装成 LLM 质量问题。
